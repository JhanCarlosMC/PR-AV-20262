# 1. Objetivo

En la guía anterior construimos el modelo de dominio del SGA: entidades, objetos de valor, agregados y servicios de dominio, con sus reglas de negocio expresadas como comportamiento.

En esta guía damos un paso igual de importante: **probar que ese modelo funciona**, y que sigue funcionando después de cada cambio.

El objetivo es aprender a escribir pruebas unitarias efectivas que demuestren que `Reserva`, `Apartamento`, `Ocupante` y los objetos de valor del SGA cumplen sus invariantes — incluidas las reglas RN-01 a RN-22 — sin depender de Spring, de H2 ni de ninguna infraestructura.

> Si una regla de negocio no tiene una prueba que la respalde, para efectos de este curso **no está implementada**: solo está escrita en un comentario.

---

# 2. Conceptos básicos

1. **Prueba unitaria de dominio.** Verifica el comportamiento de una clase del paquete `domain` en aislamiento total: sin Spring, sin base de datos, sin red.
2. **Patrón AAA.** *Arrange* (preparar el estado inicial), *Act* (ejecutar el comportamiento) y *Assert* (verificar el resultado).
3. **Aserción de estado intacto.** Además de comprobar que se lanzó una excepción, comprobar que el objeto **no cambió** cuando la regla lo rechazó.
4. **Mock.** Objeto simulado que reemplaza una dependencia externa (típicamente un repositorio) para poder probar un servicio de dominio sin construir su implementación real.
5. **Prueba de transición.** Prueba que cubre tanto una transición de estado **permitida** como una **no permitida**, de la misma familia de reglas.

---

# 3. Contextualización teórica

## 3.1 ¿Por qué probar el dominio de forma aislada?

- **Rapidez.** Al no depender de Spring Boot, bases de datos o redes, estas pruebas se ejecutan en milisegundos.
- **Confiabilidad.** Si una prueba falla, sabemos exactamente que una regla de negocio del SGA se rompió, y cuál.
- **Diseño.** Escribir pruebas obliga a mantener el dominio puro, desacoplado y orientado al comportamiento.
- **Evolución segura.** Permite refactorizar `Reserva` o `Apartamento` con confianza, sabiendo que si alguna regla se rompe, alguna prueba lo va a decir.

> El dominio debe ser la parte más rigurosamente probada de todo el SGA: es donde vive el negocio, no donde vive la tecnología.

## 3.2 Patrón AAA (Arrange, Act, Assert)

Todas las pruebas de esta guía siguen esta estructura:

1. **Arrange:** construir los objetos del dominio necesarios (una `Reserva`, un `Apartamento`, un `Ocupante`).
2. **Act:** ejecutar el comportamiento que se quiere probar.
3. **Assert:** verificar el resultado, el estado final, o la excepción esperada.

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;
```

Todas las pruebas de esta guía usan `JUnit 5`.

# 4. Parte 1: Pruebas de Objetos de Valor

Los objetos de valor se caracterizan por su inmutabilidad, su auto-validación y su comparación por valor (no por identidad). Las pruebas deben demostrar que **no pueden existir en un estado inválido** y que su lógica interna se cumple estrictamente.

## 4.1 Ejemplo: probando `IdentificacionApartamento`

Este objeto de valor tiene una particularidad interesante: normaliza su valor a mayúsculas al construirse (Guía 04, sección 6.5). Eso es exactamente lo que hay que probar, además de la validación.

```java
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class IdentificacionApartamentoTest {

    @Test
    void dosIdentificacionesConElMismoValorNormalizadoSonIguales() {
        IdentificacionApartamento a = new IdentificacionApartamento("apt-301");
        IdentificacionApartamento b = new IdentificacionApartamento("APT-301");

        assertEquals(a, b);
        assertEquals(a.hashCode(), b.hashCode());
    }

    @Test
    void debeNormalizarAMayusculas() {
        IdentificacionApartamento identificacion = new IdentificacionApartamento("apt-301");

        assertEquals("APT-301", identificacion.valor());
    }

    @Test
    void noDebeCrearIdentificacionVacia() {
        ReglaDominioException excepcion = assertThrows(ReglaDominioException.class, () -> {
            new IdentificacionApartamento("   ");
        });

        assertEquals("El apartamento debe tener una identificación", excepcion.getMessage());
    }
}
```

# 5. Parte 2: Pruebas de Entidades

Las entidades tienen identidad propia; su estado cambia mediante métodos que exponen comportamiento y protegen las reglas del negocio. Las pruebas deben validar esos cambios de estado **y** sus protecciones.

## 5.1 Ejemplo: probando la entidad `Ocupante`

```java
import java.time.LocalDate;
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class OcupanteTest {

    @Test
    void dosOcupantesConElMismoDocumentoSonElMismo() {
        // La igualdad de una entidad depende solo de su identidad
        Ocupante original = new Ocupante(new DocumentoIdentidad("CC-1000123456"), "Ana Gómez",
                LocalDate.of(1990, 5, 20), LocalDate.of(2026, 1, 1));
        Ocupante renombrado = new Ocupante(new DocumentoIdentidad("CC-1000123456"), "Ana G.",
                LocalDate.of(1990, 5, 20), LocalDate.of(2026, 1, 1));

        assertEquals(original, renombrado);
    }

    @Test
    void debeSerFacturableSiAlcanzaElUmbralALaFechaDeEntrada() {
        // Ocupante que cumple 18 el 20 de mayo; la estancia entra el 25 de mayo del mismo año
        Ocupante ocupante = new Ocupante(new DocumentoIdentidad("CC-1000123456"), "Ana Gómez",
                LocalDate.of(2008, 5, 20), LocalDate.of(2026, 1, 1));
        Estancia estancia = new Estancia(LocalDate.of(2026, 5, 25), LocalDate.of(2026, 5, 27));

        boolean facturable = ocupante.esFacturableEn(estancia, new UmbralEdadFacturable(18));

        assertTrue(facturable); // RN-06
    }

    @Test
    void noDebeSerFacturableSiAunNoAlcanzaElUmbralALaFechaDeEntrada() {
        // Cumple 18 el 20 de mayo; la estancia entra el 10 de mayo, antes del cumpleaños
        Ocupante ocupante = new Ocupante(new DocumentoIdentidad("CC-1000123456"), "Ana Gómez",
                LocalDate.of(2008, 5, 20), LocalDate.of(2026, 1, 1));
        Estancia estancia = new Estancia(LocalDate.of(2026, 5, 10), LocalDate.of(2026, 5, 12));

        assertFalse(ocupante.esFacturableEn(estancia, new UmbralEdadFacturable(18))); // RN-06
    }

    @Test
    void noDebeCrearOcupanteConFechaDeNacimientoFutura() {
        assertThrows(ReglaDominioException.class, () -> {
            new Ocupante(new DocumentoIdentidad("CC-1000123456"), "Ana Gómez",
                    LocalDate.of(2027, 1, 1), LocalDate.of(2026, 1, 1));
        });
    }
}
```

La segunda y la tercera prueba son las más importantes del bloque: **no basta con probar que RN-06 funciona; hay que probar también el límite exacto** (justo antes y justo después de la fecha de entrada), que es donde este tipo de reglas suele fallar en silencio.

# 6. Parte 3: Pruebas de Agregados (invariantes)

El agregado protege las invariantes: las reglas que **siempre** deben cumplirse. Probarlo significa intentar romperlas y comprobar que se defiende lanzando `ReglaDominioException`, **sin cambiar su estado**.

## 6.1 Ejemplo: probando el agregado `Reserva`

Observe algo importante antes de empezar: desde la corrección de la Guía 05, `Reserva.crear(...)` recibe el **identificador** del apartamento, no el objeto. Eso significa que esta prueba **no necesita construir un `Apartamento`** para probar `Reserva` en aislamiento — justamente el beneficio de esa decisión de diseño.

```java
import java.time.LocalDate;
import java.util.List;
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class ReservaTest {

    private Ocupante titular() {
        return new Ocupante(new DocumentoIdentidad("CC-1000123456"), "Ana Gómez",
                LocalDate.of(1990, 5, 20), LocalDate.of(2026, 1, 1));
    }

    /** Reserva válida del apartamento 301, del 10 al 12 de diciembre de 2026. */
    private Reserva reservaPendiente() {
        return Reserva.crear(
                new CodigoReserva("RES-2026-00001"),
                new IdentificacionApartamento("APT-301"),
                new Estancia(LocalDate.of(2026, 12, 10), LocalDate.of(2026, 12, 12)),
                titular(),
                List.of(titular()),
                CanalOrigen.PORTAL,
                LocalDate.of(2026, 1, 1));
    }

    @Test
    void debeNacerEnEstadoPendiente() {
        assertEquals(EstadoReserva.PENDIENTE, reservaPendiente().getEstado());
    }

    @Test
    void noDebeCrearReservaHaciaElPasado() {
        // Arrange & Act & Assert
        assertThrows(ReglaDominioException.class, () -> Reserva.crear(
                new CodigoReserva("RES-2026-00002"),
                new IdentificacionApartamento("APT-301"),
                new Estancia(LocalDate.of(2025, 1, 10), LocalDate.of(2025, 1, 12)),
                titular(), List.of(titular()), CanalOrigen.PORTAL,
                LocalDate.of(2026, 1, 1))); // RN-04
    }

    @Test
    void elTitularDebeSerUnoDeLosOcupantes() {
        Ocupante otraPersona = new Ocupante(new DocumentoIdentidad("CC-1000999999"),
                "Pedro Ríos", LocalDate.of(1985, 3, 1), LocalDate.of(2026, 1, 1));

        assertThrows(ReglaDominioException.class, () -> Reserva.crear(
                new CodigoReserva("RES-2026-00003"),
                new IdentificacionApartamento("APT-301"),
                new Estancia(LocalDate.of(2026, 12, 10), LocalDate.of(2026, 12, 12)),
                titular(), List.of(otraPersona), CanalOrigen.PORTAL,
                LocalDate.of(2026, 1, 1)));
    }

    @Test
    void debeConfirmarUnaReservaPendiente() {
        Reserva reserva = reservaPendiente();

        reserva.confirmar();

        assertEquals(EstadoReserva.CONFIRMADA, reserva.getEstado()); // RN-08
    }

    @Test
    void noDebeConfirmarUnaReservaYaConfirmada() {
        Reserva reserva = reservaPendiente();
        reserva.confirmar();

        ReglaDominioException excepcion = assertThrows(ReglaDominioException.class,
                reserva::confirmar);

        assertEquals("Solo una reserva PENDIENTE puede confirmarse", excepcion.getMessage());
        // El estado no debe haber cambiado tras el rechazo
        assertEquals(EstadoReserva.CONFIRMADA, reserva.getEstado());
    }
}
```

La última prueba es la más importante de las cinco: no basta con comprobar que se lanzó la excepción; hay que comprobar que **el estado quedó exactamente donde estaba**. Esta segunda verificación se olvida con frecuencia, y es la que realmente demuestra que el agregado se defendió.

# 7. Parte 4: Pruebas de Servicios de Dominio

Los servicios de dominio orquestan reglas que dependen de más de un agregado. Cuando necesitan datos que solo un repositorio puede dar, dependen de la **interfaz** del repositorio (un puerto del dominio), nunca de una implementación concreta.

> **Nota.** El patrón Repository se formaliza como tal en la **Guía 06: Casos de Uso**. Aquí solo necesitamos su interfaz, y la sustituimos por un *mock* para poder probar el servicio sin construir la implementación real.

No todo servicio de dominio necesita mocks: si solo recibe objetos del dominio ya construidos, se instancia directamente. `DisponibilidadReservaService` sí depende del repositorio, porque RN-01 exige conocer las demás reservas activas del apartamento — algo que ningún objeto en memoria de la prueba puede saber por sí solo.

## 7.1 Ejemplo: probando `DisponibilidadReservaService`

```java
import java.time.LocalDate;
import java.util.List;
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;
import static org.mockito.Mockito.*;

class DisponibilidadReservaServiceTest {

    private final ReservaRepository reservaRepositoryMock = mock(ReservaRepository.class);
    private final DisponibilidadReservaService servicio =
            new DisponibilidadReservaService(reservaRepositoryMock);

    private Apartamento apartamento(int capacidad) {
        return new Apartamento(new IdentificacionApartamento("APT-301"),
                "Balcón del Cocora", 2, capacidad);
    }

    @Test
    void noDebeAdmitirMasOcupantesQueLaCapacidad() {
        Apartamento apartamento = apartamento(2);
        Estancia estancia = new Estancia(LocalDate.of(2026, 12, 10), LocalDate.of(2026, 12, 12));

        // No hace falta programar el mock: la regla se rechaza antes de consultar el repositorio
        assertThrows(ReglaDominioException.class, () ->
                servicio.verificarDisponibilidad(apartamento, estancia, 3)); // RN-02
    }

    @Test
    void noDebePermitirSolapamientoConUnaReservaActiva() {
        Apartamento apartamento = apartamento(4);
        Estancia estanciaSolicitada =
                new Estancia(LocalDate.of(2026, 12, 11), LocalDate.of(2026, 12, 14));
        Reserva reservaExistente = Reserva.crear(
                new CodigoReserva("RES-2026-00010"), apartamento.getIdentificacion(),
                new Estancia(LocalDate.of(2026, 12, 10), LocalDate.of(2026, 12, 12)),
                /* titular y ocupantes de prueba */ titularDePrueba(), List.of(titularDePrueba()),
                CanalOrigen.PORTAL, LocalDate.of(2026, 1, 1));

        when(reservaRepositoryMock.buscarActivasPorApartamento(apartamento.getIdentificacion()))
                .thenReturn(List.of(reservaExistente));

        assertThrows(ReglaDominioException.class, () ->
                servicio.verificarDisponibilidad(apartamento, estanciaSolicitada, 2)); // RN-01
    }

    @Test
    void debePermitirCuandoHayCapacidadYNoHaySolapamiento() {
        Apartamento apartamento = apartamento(4);
        Estancia estancia = new Estancia(LocalDate.of(2026, 12, 20), LocalDate.of(2026, 12, 22));

        when(reservaRepositoryMock.buscarActivasPorApartamento(apartamento.getIdentificacion()))
                .thenReturn(List.of());

        assertDoesNotThrow(() -> servicio.verificarDisponibilidad(apartamento, estancia, 2));
    }

    private Ocupante titularDePrueba() {
        return new Ocupante(new DocumentoIdentidad("CC-1000123456"), "Ana Gómez",
                LocalDate.of(1990, 5, 20), LocalDate.of(2026, 1, 1));
    }
}
```

Observe las tres pruebas: la primera y la tercera no necesitan `when(...)` porque a la primera nunca llega a consultar el repositorio (la capacidad ya la descarta) y a la tercera el mock simplemente le contesta "no hay nada" (`List.of()`). Solo la segunda necesita programar una respuesta concreta del mock, porque es la única que depende de ella.

# 8. Precauciones y recomendaciones

1. **No pruebe getters triviales.** Una prueba que solo confirma que `getEstado()` devuelve lo que se asignó no aporta nada.
2. **Una idea por prueba.** Evite métodos de prueba con múltiples aserciones no relacionadas entre sí; si una falla, las demás dejan de informar nada.
3. **Nombre los tests por el comportamiento, no por el método.** `noDebeConfirmarUnaReservaYaConfirmada` dice más que `testConfirmar2`.
4. **Fechas fijas, nunca `LocalDate.now()`.** Una prueba que depende de la fecha del computador que la ejecuta no es reproducible; por eso `Ocupante` y `Reserva` reciben la fecha actual como parámetro desde la Guía 04.
5. **Mock solo si hace falta.** Si un servicio de dominio no depende de ningún puerto externo, instánciense sus colaboradores directamente: un mock injustificado oscurece la prueba en lugar de aislarla.
6. **Pruebe el límite, no solo el centro.** Para reglas de umbral (RN-02, RN-03, RN-06), la prueba interesante ocurre justo en el límite, no muy adentro del rango válido.
